## Context

At base `8a833d6e73d6910f838f96e0059ae6209a156c91`, TaskProfile stores model/provider/tool/skill/workspace settings but no harness identity. `task_manager.py` resolves profile fields and launches the configured task-runner image through Docker, Apple or Kubernetes container runtime interfaces. `task-runner/main.py` owns the OpenAI Agents SDK loop, native in-process `submit_result` and `/output/result.json` writing. Its HTTP callback is `/api/internal/task-result/{task_id}` in `errand/main.py`; `errand/mcp_server.py` provides profile operations, not the native result tool. Worker log parsing forwards `{type,data}` on Valkey `task_logs:{task_id}`; shared UI consumes it. The proposed external result MCP bridge is new work, not an existing implemented endpoint. SHA-linked evidence and upstream limitations are in `research.md`.

The existing Claude proposal's build spike is valuable: the distroless base needs a real Bash, correct per-architecture binaries, actual stream shapes, an HTTP MCP discriminator, and server-registration checks. Its proposed subscription-token collection is incompatible with the current documented third-party credential boundary. Its image-as-selector conflates deployment with behavior. The proposed relationship is explicit supersession of its architecture, with reuse of technical lessons, subject to Team Leader review. No archived-spec merge or edits to that proposal occur now.

## Goals / Non-Goals

Goals: independently persisted selection per profile; unchanged built-in execution; a small qualified adapter set; enforceable isolation; trustworthy outcomes/accounting; honest capability gaps; extensibility without arbitrary executable injection.

Non-goals: implement all researched harnesses, emulate missing upstream approval APIs, choose a harness from model branding, transplant vendor internal safety nets, guarantee exactly-once arbitrary network effects, support unqualified host/kernel combinations, share session homes across tenants, or provide subscription-token brokerage. Classification/intake LLMs remain existing provider-based services; changing the execution harness does not replace them.

## Decisions

### 1. Identity and persistence

Add `harness_id` (non-null string, server/database default `builtin`) and `harness_config` (JSON object, default `{}`, adapter-validated with `schema_version: 1` when populated) to TaskProfile. Stable ids proposed: `builtin`, `claude-code`, `codex`, and later qualified `pi`, `hermes`, `opencode`, `deepseek-harness`. Only registered ids are accepted for new writes. `phi` is rejected as ambiguous, not normalized silently. Microsoft Phi can be selected as a model only when an existing provider supports it; DeepSeek API remains a provider distinct from `deepseek-harness`.

Configuration holds credential references, permission policy references, optional supported model/provider override, resume preference and bounded budgets, never secrets, command strings or arbitrary image URLs. Registry determines exact executable/image/protocol versions; profile references an approved release track, not a mutable latest tag. Existing `model`/provider fields retain semantics for builtin; external adapters must validate supported bindings or require explicit adapter-specific bindings. Do not silently send arbitrary LiteLLM model aliases to Claude/Codex. Preserve inactive model fields when switching away and back.

PUT/PATCH semantics: omission preserves existing selection, explicit `builtin` switches, null/unknown/malformed config returns 422. Create/clone/export/import and MCP operations carry identity/config; export strips credentials and imports require references to be rebound. Old clients omitting fields create builtin and cannot reset an existing external selection by omission. Existing default-profile/tag-resolution precedence is unchanged. A profile absent at dispatch resolves the legacy default with builtin. Harness selection is per profile, never inherited from a global preferred harness. Registry availability is global deployment policy, not a substitute for profile intent.

### 2. Adapter registry and negotiation

Registry entries are deployment-controlled, versioned manifests: id, adapter version, config schema, vendor version, protocol schema/hash, digest-pinned image per architecture, executable checksum, runtime allowlist, legal/auth modes, tool ownership, feature states and qualification record. Capability states: supported (qualified tuple), unsupported (known absent), unknown (not proven), experimental (explicit opt-in). Documented upstream functionality does not mark an Errand tuple supported.

Contract operations: inspect/validate configuration, negotiate required capabilities, prepare, start, observe normalized events, collect/validate result, cancel, cleanup; optional resume and approval response. These are conceptual interfaces, not code in this change. Required baseline: non-TTY automation, isolated runtime, scoped MCP/tool policy, authoritative result validation, bounded shutdown, redaction and parseable terminal errors. Features include structured native result, tool events/call ids, per-turn usage, total/session usage, cost, resume, approval interaction, native sandbox, skills/plugins, network policy and cancellation mode.

Resolve and revalidate at dispatch. Required unsupported/unknown capability fails before launch with actionable `capability_unavailable`; optional telemetry gaps produce warnings and null values, not false data. Plugin/skill format compatibility is not assumed: translate vetted markdown where supported, prohibit auto-loading executable extensions and arbitrary project hooks; declare plugin gaps or reject profiles requiring them. No dynamic installation from task content. Admin extension entries must pass the same conformance suite; they are not shell templates supplied by end users.

### 3. Ownership and process lifecycle

Errand retains task scheduling, attempt leases, permissions, scoped service access, result finalization, retries and durable audit. Adapter/harness owns its model loop, internal context compaction and native local tools. Do not nest the full builtin loop around an external loop or run both on the same attempt. Wrap builtin with a behavior-preserving adapter, keeping its compaction/stall guards; external guards are declared separately, not claimed inherited.

Attempt lifecycle: queued -> preparing -> running -> succeeded/failed/cancelled/timed_out; preparation failure is terminal for that attempt. Internal `awaiting_approval` substate is reserved but interactive approvals are not phase-1 functionality. Phase 1 uses deny-by-default unattended permissions; an unanswerable required approval terminates with `approval_required`, not a blocked TTY. Terminal persistence uses attempt lease/fencing token and compare-and-set so one outcome wins. Task-level states map through existing lifecycle rules; do not add public statuses until separately reviewed.

At launch capture immutable profile revision, harness/config hash, adapter/vendor versions, image digest, runtime/architecture, model/provider, permission and tool catalog hashes, credential reference id (no value), budgets and input/artifact hashes. Running attempts are unaffected by profile/registry edits. Each attempt gets isolated HOME/XDG/vendor directories, workspace, process tree, session store and short-lived task principal. Cleanup runs on success, failure, cancellation and worker recovery. No host home, socket, kubeconfig, profile database or unrestricted shared workspace mounts. Task files are content, not trusted executable configuration. Bound CPU, memory, process count, disk, stdout/event sizes and wall time.

Use approved derived images with required Bash/libraries, never assume busybox/distroless works for all binaries. Disable vendor auto-update using qualified deployment controls without modifying proprietary binaries or removing authentication mechanisms. Qualify Docker Linux amd64/arm64 first. Apple VM/runtime and Kubernetes are separate release tuples with network/filesystem containment and image/secret delivery tests; default deny until passed. Codex sandbox nested-container/user-namespace constraints must not trigger automatic unsafe bypass; an approved outer sandbox can be negotiated explicitly and audited. This proposal is not a claim that the analyst's old Linux kernel qualifies any external runtime.

### 4. Secrets and legal boundaries

Reuse/extend encrypted sensitive-setting infrastructure with principal/profile binding, ACL checks, masking and credential references. Resolve only selected adapter's credentials just in time; inject via protected ephemeral files or minimal process environment where required, never argv, prompts, image layers, vendor project configs, events, exports or debug archives. Do not promise secrecy from the harness process that must use the credential: isolate it, minimize scope and revoke on teardown. Subprocess/tool environment scrubbing is mandatory where available; prefer brokered service credentials outside the container. Explicitly test inherited environment leakage. Rotate/revoke and surface expiry without fallback.

Claude launch uses authorized customer's API key or supported cloud credentials initially. Current official docs prohibit third-party collection/storage/intermediation of Claude.ai session credentials while permitting end-user direct sign-in to an unmodified binary under stated conditions. Consequently the old `claude setup-token` Settings card is NOT implemented by this proposal. If direct vendor-owned subscription login is wanted, desktop/auth/legal owners must approve a separate flow, isolation and retention design. Do not modify the binary or remove authentication choices; legal review must reconcile controlled unattended launch settings with upstream product conditions before distribution. Codex account/API entitlement and all other provider terms require review; open-source harness license never waives inference service terms. Budgets/cost are not assumed zero for subscriptions.

### 5. Enforceable permissions and tool ownership

Policies are enforced outside prompts: container/VM boundaries, non-root execution, dropped capabilities, no privileged mode/host daemon sockets, restricted mounts, read-only roots where practical, seccomp/runtime controls, outbound network proxy/allowlist and scoped MCP gateway. Native approvals/hooks are defense in depth, not a sandbox. A task cannot grant itself wider policy. No blanket dangerous bypass as an automatic workaround.

Use task-scoped MCP broker credentials with allowed tools/server transports validated at preparation. The current shared API-key scope is insufficient to claim per-task authorization: implement task-scoped MCP gateway authorization before external rollout. Deny eval/admin/profile mutation/secret-management tools by broker authorization, not just client tool exclusion. Required-server handshake + expected allowed catalog check must fail launch if a configured server disappears silently. Local stdio servers run inside the same isolated boundary with pinned executables; remote HTTP uses scoped headers/TLS. Do not forward global MCP config, unreviewed URLs, cross-profile sessions, or recursively expose a harness adapter as a self-delegation tool.

Define a single owner for each capability: external native filesystem/shell tools inside the sandbox; Errand broker owns messaging, cloud/workspace services, memory service and result submission; duplicates disabled or namespaced distinctly. Builtin native tools remain unchanged. Result submission broker method is trusted only after identity, schema and attempt fencing validation. Standard MCP is the integration baseline; ACP/JSON-RPC/vendor HTTP are adapter control protocols, not interchangeable MCP tool transports. System instructions/skills are content-translated through declared formats; Hindsight memory remains scoped and optional, vendor auto-memory cannot become shared tenant state.

### 6. Results, events, usage and observability

A normalized terminal record contains schema version, task/attempt id, fencing token, status, validated existing Errand output object, artifact references, error, usage, exit code, session reference and provenance. The external supervisor emits legacy `agent_end` and writes existing `/output/result.json` only for validated success. The output payload retains `status` (`completed` or `needs_input`), required string `result`, and `questions` (array of strings, default []); a successful needs_input payload maps to the existing task input-needed behavior, not task completion. Native builtin submit_result normalization (including string-encoded questions and last-submission-wins), text-JSON/plain-text fallback and existing nudge behavior are preserved unchanged. External adapters use stricter candidate rules: native structured output or the new scoped result MCP bridge is accepted only if the harness also terminates successfully; candidate submission alone does not finalize an active attempt. Conflicting external candidates, malformed JSON, missing required output or nonzero exit become explicit failures. The external supervisor makes one fenced durable finalization; callback/file delivery is deduplicated by attempt, with callback completion staged until supervised exit verification. Raw vendor stdout is never external result fallback. No external model re-run solely to repair a malformed result after potential side effects. This does not remove the canonical builtin output extraction priority or its existing empty-response nudge.

Preserve stderr `{type,data}`, Valkey `{event:task_event,type,data}`, `task_log_end`, 500-character tool result previews and diagnostic exclusions. Add metadata inside `data` (protocol version, attempt, sequence, native call id, harness/vendor version); maintain legacy consumers. Map native system/start -> agent_start; message -> thinking; tool start/end -> tool_call/tool_result; success -> agent_end; terminal/parse failures -> error. Emit additive harness_status/usage/permission_denied/unknown-event summaries with bounded redacted payloads. Unknown event variants never imply success. Concurrent tool results use call ids; do not pair by name alone. Expose only supported reasoning summaries; do not synthesize or persist hidden chain of thought. Backpressure coalesces optional text but cannot drop terminal state/errors.

Usage fields distinguish input/output/cache/reasoning tokens where documented, currency, cost, elapsed time, source (reported/estimated/unavailable), completeness and scope (turn/attempt/session). Unavailable values are null, not 0. Do not fabricate turn boundaries from external total usage. Resumed session cumulative costs are differenced only with stable scoped counters; reset/fork/crash gaps remain unknown and never double-counted. Estimated cost is not invoiced spend; display external subscription quota separately if documented. A requested hard dollar cap is accepted only with enforceable upstream/proxy enforcement; polling totals is a soft warning, not a strict guarantee.

Persist normalized attempt outcome plus bounded redacted events/artifact references under existing retention/RBAC. Metrics: preparation/launch latency, outcomes, cancel latency, broker denied calls, parse failures, capability mismatches, retry suppression, usage completeness. Labels use bounded harness/version/runtime values, no task/user/secret cardinality; tracing joins task/attempt with access controls. External internal compaction, stalls and hidden tool activity are reported unavailable unless exposed. Coordinate active context-accounting/usage proposals to avoid pretending SDK-only counters apply to external loops.

### 7. Cancellation, retry, timeout, resume and concurrency

Wall timeout applies end-to-end including startup/provider backoff; phase defaults: use current task timeout policy, with configurable bounded startup and shutdown budgets (recommended startup 60s, graceful cancel 10s, kill/cleanup 10s; exact defaults require Team Leader approval). Cancellation first revokes/fences service capability, sends documented protocol interrupt/SIGTERM, waits bounded grace, then kills the entire process/container tree and reconciles runtime deletion. Track partial effects and uncertain cleanup; a missing process does not prove an outbound request was undone. Worker restart recovers leases, reconciles orphan containers and prevents duplicate finalization.

No automatic cross-harness fallback, even for preflight auth failure; fail visibly and preserve intent. Retry only classified transient preparation failures or proven side-effect-free attempt failures within the existing capped task retry budget. After any native shell/network tool starts, broker mutation starts, or event stream is incomplete, effects are possible/unknown and automatic replay is prohibited unless a scoped idempotent operation contract proves safety. Upstream in-process retries count toward wall/budget limits and must not combine into worker retry storms. Auth, policy denial, unsupported versions and malformed output are non-retryable. Manual retry warns about partial effects and records authorization.

Resume is disabled in initial external rollout. Later it requires qualified native resume, explicit profile opt-in, exclusive lease, same principal/task/profile revision, compatible pinned adapter/vendor/model/policy/catalog, encrypted session/artifact storage with retention TTL and deletion, and reauthorization of credentials. Resume is not rollback or exactly-once replay. Reject missing/cross-tenant/stale version references; never use implicit “last session”. Separate attempt and session accounting. Shared vendor account quotas are enforced via per-credential concurrency limits plus current global semaphore and deployment quotas. Per-profile fairness/limits prevent one external harness starving builtin work; one session writer at a time. No warm shared vendor server across users in initial phases.

### 8. API, UI and coordinated boundaries

Extend existing profile CRUD, clone and MCP profile tools; add authenticated `GET /api/harnesses` returning deployment-qualified ids/releases/capabilities/auth requirements/availability reasons with no secrets. Runtime-qualified discovery is authoritative; unavailable persisted selections remain visible and produce a dispatch error. Profile writes return 422 for unknown/config-invalid values and reject newly selecting unavailable releases; existing unavailable profiles may still edit unrelated fields. Permission RBAC follows current profile settings controls; credential binding adds principal/profile authorization. Include harness snapshot/outcome/nullable usage in task read endpoints without changing legacy output fields. No new approval UI in phase 1; future interactive approval needs its own RBAC, correlated request ids, TTL and audit spec.

Shared TaskProfileListCard must separate Harness from Model/Provider, retain builtin defaults and saved values, show capability gaps and disabled runtime entries, and never present research-only adapters as supported. TaskLogViewer must tolerate additive events and pair native call ids with fallback for legacy streams. Main repository wrappers/tests/dependency bumps integrate separately versioned ui-components release. Desktop/cloud APIs must not infer support merely from container runtime name. OpenSpec proposals in those repositories are prerequisites for their implementation.

## Migration and rollout

Expand migration adds defaulted fields and attempt provenance storage with backfill to builtin. Release readers tolerant of absent fields first, then writers, then builtin adapter extraction with golden-result/event tests. Mixed old workers may execute only builtin tasks; registry/dispatch routing must prevent them claiming external tasks. Older clients can read/add fields and preserve selection. Downgrade is blocked while external configurations/runs exist unless an explicit export/rebind-to-builtin procedure is approved; never drop identities silently. No migration of `container_image`/OAuth-token fields is assumed since the old change is unimplemented at base; if merged concurrently, stop and reconcile migration/supersession before rollout.

Phase 0: Team Leader supersession/legal/security approval and contracts; no external feature advertised.
Phase 1: schema/discovery, immutable snapshot and builtin adapter; gates require behavior parity and mixed-version routing.
Phase 2a: opt-in Claude Code Linux Docker tuple, authorized API/cloud billing and conformance; only then expose available UI entry.
Phase 2b: independently qualified Codex exec tuple; app-server stdio is future approval-rich alternative, not an assumed stable production service.
Phase 3: independently proposed Pi/Hermes/OpenCode qualification and resume. DeepSeek Harness stays experimental research-only until security/maturity review. Gemini consumer product transition warrants reassessment before choosing Gemini/Antigravity.

Rollback disables new external dispatch/selection and drains/cancels existing attempts per policy; preserves external selections with unavailable reasons rather than coercing them to builtin. Builtin remains continuously available. Documentation work follows actual implementation verification and names only qualified tuples.

## Risks / Trade-offs

Registry+broker adds complexity but is safer than arbitrary images/executables. Dedicated process/container per attempt costs startup time but avoids account/session leakage. Vendor CLI JSON evolves; pins and fixtures limit drift but increase maintenance. External loops may lack builtin stall/compaction/cost telemetry; expose gaps instead of porting brittle internal hooks. Refusing transparent fallback reduces apparent availability but avoids duplicate messages/payments. API-key-first Claude avoids prohibited token storage but does not satisfy the original subscription-capacity goal; direct vendor login is an unresolved, separately gated product decision. Native tools improve harness fidelity but require robust outer isolation and careful duplicate-tool policy. No system can undo arbitrary external side effects just by cancelling a process.

## Validation strategy

Strict OpenSpec validation checks structural coherence, not executable safety. Future implementation acceptance requires migration/old-client/MCP round trips, builtin golden fixtures, registry version/runtime failures, mock+real pinned protocol tests, duplicate/partial result and stream truncation tests, cross-profile secret/MCP/workspace escape attempts, process-tree shutdown, worker-crash fencing, side-effect retry suppression, quota concurrency, unavailable/unknown telemetry and UI shared-component compatibility. Test each approved runtime/architecture/auth tuple and publish evidence before enabling it. All implementation tasks remain unchecked in `tasks.md`.
